# ADR-0001: 采用 Monorepo 结构（先合后拆）

**状态**：已采纳
**日期**：2026-08-31
**阶段**：P1

---

## 背景

Helix ECO Glove 项目需要支持多个平台（macOS、Linux、Windows、Harmony、Android、Robot 等）。在项目初始化阶段，需要决定采用何种仓库结构：

1. **Monorepo**：所有平台手套在一个 Cargo workspace 中，成熟后再拆分
2. **多仓库**：每个平台手套一个独立仓库
3. **单仓库**：所有手套在一个 crate 中，用 feature flag 控制

## 候选方案

### 方案 A：Monorepo（先合后拆）

所有平台手套在一个 Cargo workspace 中，每个手套是独立的 crate。当某个手套成熟到"外部项目想单独依赖它"时，再用 `git subtree split` 拆分为独立仓库。

**优点**：
- 公共接口（EcoGlove trait）修改时，可以一次性调整所有实现
- 跨平台测试和集成测试方便
- 新平台手套可以快速复用现有代码和工具
- 避免"为了独立而独立"，符合"极致节能"哲学

**缺点**：
- 仓库体积会逐渐增大
- 单个手套的发布需要 workspace 级别的版本管理

### 方案 B：多仓库

每个平台手套一个独立仓库，通过 crates.io 或 git 依赖共享 core crate。

**优点**：
- 每个手套可以独立发布和版本管理
- 仓库体积小
- 外部项目可以只依赖需要的平台手套

**缺点**：
- 公共接口修改时，需要跨仓库同步，容易遗漏
- 跨平台测试困难
- 新平台手套需要重复搭建项目骨架
- 过早拆分，违背"DNA 方法论驱动演化"哲学

### 方案 C：单仓库 + feature flag

所有手套在一个 crate 中，用 feature flag 控制编译哪些平台。

**优点**：
- 结构最简单
- 依赖管理最方便

**缺点**：
- 单个 crate 体积过大
- feature flag 组合爆炸
- 无法独立发布单个平台手套
- 不符合"极致解耦"哲学

## 决策

**采用方案 A：Monorepo（先合后拆）**。

理由：
1. 符合 Linux 内核和 Rust 编译器的最佳实践——模块先在 tree 里长着，等边界清晰、需求稳定了再拆分
2. 避免"为了独立而独立"，符合"极致节能"和"DNA 方法论驱动演化"哲学
3. 公共接口修改时可以一次性调整所有实现，减少跨仓库同步成本
4. 新平台手套可以快速复用现有代码和测试框架
5. 成熟后可以用 `git subtree split` 无损拆分为独立仓库，不丢失历史

## 后果

### 正面
- 开发效率高，新平台手套可以快速启动
- 公共接口演进顺畅
- 跨平台测试和集成测试方便
- 符合"先合后拆"的务实生长节奏

### 负面
- 仓库体积会逐渐增大，需要定期清理
- 单个手套的发布需要 workspace 级别的版本管理
- 需要明确"成熟"的定义和拆分标准

## 拆分标准

当一个平台手套满足以下所有条件时，可以考虑拆分为独立仓库：

1. 功能稳定，6 个月内没有重大接口变更
2. 有外部项目明确表示想单独依赖此手套
3. 测试覆盖率 ≥ 90%
4. 文档完整，有独立的 README 和使用示例
5. 与 core crate 的接口稳定，不需要频繁同步修改

拆分时使用 `git subtree split`，保留完整的 git 历史。
